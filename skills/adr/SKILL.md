# Запись архитектурного решения

Решение, которое не записано, через месяц принимают заново. Запись короткая: её должны прочитать за две минуты.

## Как принимать

1. **Выясни ограничения до вариантов.** Объём данных и нагрузка, сроки, кто будет поддерживать, бюджет, что уже есть в проекте (читай код и конфиги, не угадывай), цена ошибки и цена отката.
2. **Два-три реальных варианта.** Включая «ничего не менять», если это честный вариант. Для каждого: что даёт, чего стоит сейчас, чего стоит потом, насколько обратим.
3. **Рекомендация одна.** С причиной, привязанной к ограничениям из шага 1, а не к моде.
4. **Проверь опасное.** Если решение держится на предположении (библиотека умеет X, сервер выдержит Y) — проверь его маленьким прототипом или пометь как непроверенное.

## Шаблон записи

Файл `docs/adr/NNNN-короткое-название.md` в репозитории проекта (номер — следующий по порядку). Если репозитория нет — в память проекта.

```markdown
# NNNN. Название решения

Дата: ГГГГ-ММ-ДД · Статус: предложено | принято | заменено NNNN

## Контекст
Что происходит и почему решать нужно сейчас. Ограничения — списком, с цифрами.

## Варианты
### А. ...
Плюсы / минусы / цена / обратимость
### Б. ...

## Решение
Выбрали ... потому что ...

## Последствия
Что станет проще, что сложнее, что нужно сделать (задачи с исполнителями).

## Когда пересмотреть
Конкретное условие: «если записей больше 1 млн», «если появится второй сервер».
```

## Чего не делать

- Не выбирать «на вырост» без названной причины роста.
- Не переписывать работающее ради красоты: у переделки должна быть измеримая польза.
- Не прятать неудобный вариант: если он отвергнут, в записи видно почему.
